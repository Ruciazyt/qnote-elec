## 1. 唯一测量口径（2026-11-05 定死）

文档里所有对比度数字只能出自这一套，写进 `docs/UI-GUIDELINES.md` 第四节：

1. WCAG 2.x 相对亮度公式，sRGB 线性化阈值 `0.03928` 与 `0.055`。
2. HSL 按 CSS 规范转 sRGB，**结果保留浮点，不取整到 8-bit**。
3. 透明档：**先把源色与实际底色做 alpha 合成，再算对比度**（不能拿半透明色直接比）。
4. 底色只有两种：`--card`（`0 0% 100%`）与 `--background`（`0 0% 98%`）。
5. 同一个组合对两种底色各给一行，**结论取更差的那个**。
6. 判定线：正文与图标文字 4.5:1（AA）、大号文字 3:1、非文本图形元素 3:1。

口径的参考实现（本报告全部数字的来源，与 `scripts/check-contrast.mjs` 应逐数对齐）：

```js
const h2r = (h, s, l) => {                       // CSS 规范 HSL → sRGB，保留浮点
  const a = s / 100, b = l / 100;
  const c = (1 - Math.abs(2 * b - 1)) * a, hp = h / 60;
  const x = c * (1 - Math.abs((hp % 2) - 1));
  let r, g, bl;
  if (hp < 1) [r, g, bl] = [c, x, 0];
  else if (hp < 2) [r, g, bl] = [x, c, 0];
  else if (hp < 3) [r, g, bl] = [0, c, x];
  else if (hp < 4) [r, g, bl] = [0, x, c];
  else if (hp < 5) [r, g, bl] = [x, 0, c];
  else [r, g, bl] = [c, 0, x];
  const m = b - c / 2;
  return [r + m, g + m, bl + m].map(v => v * 255);
};
const lum = ([r, g, b]) => {
  const f = v => { v /= 255; return v <= 0.03928 ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4); };
  return 0.2126 * f(r) + 0.7152 * f(g) + 0.0722 * f(b);
};
const cr = (c1, c2) => {
  const l1 = lum(c1), l2 = lum(c2);
  return (Math.max(l1, l2) + 0.05) / (Math.min(l1, l2) + 0.05);
};
const over = (fg, a, bg) => fg.map((v, i) => v * a + bg[i] * (1 - a));  // alpha 合成
```

> 若改用「HSL→sRGB 后取整到 8-bit」的浏览器实际绘制口径，全部数字会偏移 ≤0.03，
> **没有任何一个数跨越 4.5 或 3:1 的判定线**，结论完全一致。取整与否只在小数第二位上，
> 两种实现都不算错，但文档只能有一套 —— 本报告采用上面这套。

> **2026-11-05 晚补全**（质量发版复核出的顺序坑，原文只写了「改哪两处」，

1. `scripts/release/verify-version.js:36` 的 `const RELEASE_LINE = { major: 1, minor: 8 };` → 改成 `{ major: 1, minor: 9 }`。
   不改的话 `pnpm run verify:version` 与 `pnpm run release:minor` 会被拦。
2. 根 `package.json` 的 `version` 由 1.8.0 → 1.9.0 —— **版本号唯一来源就是这一个字段**，别处不得另造。
   ⚠️ 但**不要手工改这个字段**：它是 release 脚本第 7 步 `pnpm version minor` 的结果，
   手工先改成 1.9.0 的话脚本会再 bump 一次成 **1.10.0**。
3. 本批有 `feat` → 必须 minor，不能发 patch。
4. **顺序**：先提「切线」提交（只改 `RELEASE_LINE`）→ 再跑 `pnpm run release:minor`。
   脚本第 7 步才 bump、第 8 步才校验发布线，顺序反了会留下
   「package.json 已 bump 但没提交没 tag」的半完成状态。
5. **切线提交不能单独 push**：CI 的 verify-version 步骤是无参调用，走的是带发布线判定的
   完整校验。`RELEASE_LINE` 已是 1.9 而 `package.json` 还是 1.8.0 时，master 的 Auto Build 会红。
   切线提交必须跟 bump 提交一起推。

**关于 1.8.1 这个版本位**：本批直接发 1.9.0，1.8.1 不用。
`1.8.0..origin/master` 那 23 个提交单独看是合法的 patch，但本地 master 已经领先，
release 脚本 bump 的是本地 HEAD、会把本批的 feat 一起算进去 → 只能出 1.9.0。
那 23 个提交从未 bump 过 `package.json`（版本号一直是 1.8.0），
「1.8.1」在版本号层面从来没存在过，只是口头叫法；
要单独切出来必须在中间某个提交上手工改 `package.json` 再打 tag，
绕过脚本、多一道手工版本操作，违反「版本号唯一来源是 package.json」。
