QNote · 插件系统

一个插件从文件夹到市场分发，要过哪几道闸

插件 = 一个文件夹 + 一份 plugin.json。宿主只做三件事：读清单、跑进程、管权限。 下面这条链路把「创建 → 导入注册 → 启动运行 → SDK 交互 → 发布分发」串起来， 标出每一段的判定点与落点文件。

「市场来源 + 指纹比对」这一步就是权限闸门 ①

权限模型

三道闸门，越往后越即时

前两道是「插件是不是可信」，第三道是「用户此刻还允不允许」。

闸门 ① · 市场来源的启动确认

只有 origin = market 的插件才要确认。确认框展示插件名、完整命令行、风险分析、声明的权限；确认后把清单指纹写进 confirmed_manifest_hash。

清单一改，指纹对不上，下次启动再问一次 · core/plugin/runtime/pluginManager.ts · pages/plugin/runtime/StartConfirmDialog.tsx

闸门 ② · 清单声明的 capabilities

没声明就是最小权限 —— 只能加载预览页面，起不了子进程、读不了笔记待办。checkCapability 是纯函数，每次数据类调用现判，不做启动时的一次性放行。

越权调用 → 拒绝 + 写进插件自己的日志，不弹窗打断 · core/plugin/permissions/capabilities.ts

闸门 ③ · 用户逐项授权（plugin_grant）

清单里声明的权限拆成一项一项（读笔记 / 写笔记 / 读待办 …），存进 plugin_grant。设置页能逐项查看与撤销，撤销后下一次调用立刻失败，不用重启插件。

判定收在 hostApi.requireCapability 一处 —— 清单声明 + 用户授权两道都要过 · core/plugin/permissions/pluginGrants.ts

运行态

状态机

stateDiagram-v2
  [*] --> inactive
  inactive --> activating : startPlugin
  activating --> active : SDK 握手成功
  activating --> active : 没接 SDK · 按普通程序跑
  activating --> failed : 握手失败
  active --> deactivating : stopPlugin
  deactivating --> inactive : 进程已收
  active --> failed : 异常退出
  failed --> inactive : 重启
「没接 SDK」单独一条：很多插件只是普通程序，不该被标成启动失败

④ SDK 交互

插件怎么跟宿主说话

插件是独立进程，跟宿主之间只有一条 loopback HTTP + 回调注册通道，插件碰不到 SQLite。

sequenceDiagram
  participant P as 插件进程
  participant SDK as plugin-sdk.js
  participant R as rpcServer
  participant A as hostApi
  participant DB as SQLite / QNote 数据
  P->>SDK: 进程起来
  SDK->>SDK: listen(0, 127.0.0.1) 起回调服务
  SDK->>R: POST /register-callback { port }
  R-->>SDK: { ok: true } ← 注册成功即接通
  P->>SDK: ctx.notes.list()
  SDK->>R: POST /rpc (x-qnote-token)
  R->>A: handlePluginCall(method, params)
  A->>A: checkCapability 清单声明
  A->>DB: 读 plugin_grant
  alt 声明了 且 没被撤销
    A->>DB: 读笔记 / 待办 / 剪贴板
    A-->>R: 结果
  else 越权 或 已撤销
    A-->>R: error + 写插件日志
  end
  R-->>SDK: JSON-RPC 响应
  SDK-->>P: 返回值
宿主主动调插件只有三个方法：plugin.activate / plugin.deactivate / qnote.command.invoke

⑤ 发布分发

发布前先拦一道网关约束

发布前检查

公共目录前面挂的是 AWS ALB，它扫整个请求，URL / query / body 里出现带 scheme 的 IP 字面量就返回 403。 本地先拦比发布后吃 403 好。

preview.url
有 IP 字面量 → 拒发，提示改用 type: "port"
runtime.env
值里有 IP 字面量 → 拒发
capabilities.network
模式里有 IP 字面量 → 拒发
放行边界
http://localhost、不带 scheme 的 127.0.0.1:7799 都放行

市场条目

published_app 存三样：清单、资源包、版本信息。本地 SQLite 与 TiDB Cloud 两套后端语义一致。

version
插件版本 —— 装的是指定版本，不是「最新版」
dependencies
JSON 数组 —— 依赖的插件 id 与版本范围
bundle
资源包（base64 + deflateRaw），清单单独走 manifest 字段
升级
覆盖清单与资源包 → 清掉确认指纹 → 下次运行重走一次权限确认
依赖缺失或版本不满足 → 拒绝激活并指明缺哪个，不做自动安装（避免装一个插件顺手装一堆东西），错误文案里带「请到插件市场手动装好依赖」的指引。

目录

跨四层，同一套模块名

同域文件不堆在一个目录里 —— 共享层、主进程、IPC、渲染层各自分子目录，模块名一一对应。

manifest

  • shared/plugin/manifest/ — 类型、清单解析校验、preview 形态
  • core/plugin/manifest/ — 清单读写落盘
  • pages/plugin/manifest/ — 清单编辑器

runtime

  • core/plugin/runtime/ — pluginManager、状态机、资源包
  • pages/plugin/runtime/ — 插件列表、日志台、预览面板
  • core/window/plugin/runtime/ — 预览协议

permissions

  • shared/plugin/permissions/ — 授权词表、风险分析
  • core/plugin/permissions/ — checkCapability、plugin_grant
  • pages/plugin/permissions/ — 授权面板

dependencies

  • core/plugin/dependencies/ — extensionDependencies 解析与比对
  • 版本比对复用 satisfiesRange

sdk

  • shared/plugin/sdk/ — 协议类型
  • core/plugin/sdk/ — rpcServer 传输层、hostApi API 面
  • resources/plugin-sdk/ — 插件侧纯 ESM SDK

market

  • shared/plugin/market/ — 版本比较
  • core/plugin/market/ — 发布前检查、版本与依赖读写
  • pages/plugin/market/ — 市场列表、发布框

migration

  • core/plugin/migration/ — 1.x 老应用幂等迁移
  • pnpm run migrate:plugins 可单独跑

dialog

  • shared/plugin/dialog/ — 弹框协议类型
  • handlers/plugin/dialog/ + core/window/plugin/dialog/
  • pages/plugin/dialog/ — 弹框宿主页面

入口留根

  • 渲染层路由页 pages/plugin/PluginsPage.tsx
  • 主进程主控 core/plugin/runtime/pluginManager.ts
  • 其余全部下沉到模块子目录
