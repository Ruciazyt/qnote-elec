# Pixel Pet —— 确定性像素宠物生成

## 何时用这个 Skill

- 想把一个静态 UI 图标（机器人、齿轮、默认 avatar）换成有性格的角色
- 需要多帧循环动画（呼吸、眨眼、待机、思考/加载）
- 要产出符合像素画硬约束的资源：硬边、无抗锯齿、限定色数

## 核心原则：不要用生图模型画像素画

**这是本 Skill 最重要的一条。**

AI 生图模型做像素画的失败模式不是"画得丑"，而是稳定地返回
「看起来**像**像素画的插画」：

- 边缘带抗锯齿的灰阶过渡（软边）
- 落在任意网格上，不是你要求的整数网格
- 尺寸不对，32×32 的要求给你 1024×1024
- 每帧之间角色长相漂移，拼接成 spritesheet 后帧间跳变

这类图**无法通过后处理可靠修复**。去色、缩放、阈值化都会破坏细节，
重画一帧的时间和手工验证 14 帧差不多。

**所以：用图元程序化绘制。** 每个像素的落点由代码决定，
改一个参数就能重出整套帧，帧间一致性由构造方式天然保证。

本 Skill 的实现见 `src/`：
- `pet.mjs` — 画布、调色板、动画元数据
- `maltese.mjs` — 角色绘制：马尔济斯犬（图元 + 描边 + 五官）
- `cat.mjs` — 备用角色：橘猫
- `build.mjs` — 帧配方、PNG 编码、图集合成；顶部一行切换当前角色

## 像素画的硬约束

违反任意一条就会看起来"不对"，且不是审美问题而是技术问题：

1. **必须整数倍缩放**。32px 单元格 → 64px 是整数倍，边界落在像素格上。
   缩放到 56px 这类非整数倍会产生半像素边界，边缘发虚。
2. **必须 `image-rendering: pixelated`**。浏览器默认双线性插值，
   像素块之间被混出半透明灰边，整张图像"糊了的像素画"。
   这是像素渲染最常见的失败，且不会报错，只会看起来不对。
3. **禁止对精灵图做 `scale()`**。`image-rendering: pixelated` 只在**尺寸固定**时有效；
   一旦加 `transform: scale(1.04)`，浏览器会按新尺寸重新采样位图，
   像素块宽度变成 2px/3px 混杂，锐利边缘当场糊掉。
   要做交互反馈就用**整数像素位移**（`translateY(-2px)`）——位移是合成层操作，
   不触碰像素本身，因此完全安全。
   同理要避开 Tailwind 的 `zoom-in-*` 入场动画。
4. **必须限定色数**。8-16 色是常态。写"复古色调"没用，要写
   "限定 16 色，柔和土色系"。色数不设上限必然出脏。
5. **描边要在五官之前**。统一勾边若在五官之后跑，会把眼白、
   眼内高光一并判成"边缘"涂成黑色，眼睛糊成一团。
   顺序是：形体 → 描边 → 五官。

## 帧数与节奏

动作多不等于帧多，节奏比帧数更影响观感：

| 状态 | 帧数 | fps | 理由 |
|---|---|---|---|
| 待机 | 4-6 | 2-2.5 | 待机要慢。快节奏的待机显得焦躁 |
| 思考/加载 | 6-8 | 5-6 | 必须明显快于待机，状态差异要一眼可辨 |

单帧位移控制在 1-2px。32px 网格上 3px 以上的位移会显得抽搐。

**循环动画的接缝**：首帧与末帧的参数必须能自然衔接。
呼吸用对称起伏（`0 → -1 → -1 → 0 → 1 → 0`），
附属部件的相位走完整一轮（六相就是 `0 → 1 → 2 → 3 → 4 → 5 → 0`），
否则循环点会出现部件瞬移或身体跳变。

## 尾巴这类附属部件的常见坑

**厚度阈值：部件每个方向的厚度必须 ≥5px（含描边）。**
描边吃两侧各 1px，所以 2px → 剩 0px（全被吃光）、3px → 剩 1px（勉强）、
5px → 剩 3px（可读）。这是"细部件消失"的通用阈值，
**与线宽无关，只与描边宽度有关**——调粗线宽解决不了它。

32px 网格上，摆幅 2px 的尾巴**肉眼分辨不出在动**，
等于白写。要让摆动可见：

- 摆幅至少 3px
- 绘制 4-6 个相位，且相位走完整圆周
- 尾尖用不同色做视觉锚点，否则运动模糊感会让摆动读不出来

## 附属细节必须"贴体"，否则读成杂线

像素画的像素数极少，每一根细节都要对得起它的语义：

- **胡须**太长会脱离身体，3px 的游离黑线看起来就是一根划痕，而不是胡须。
  收到 1-2px 并贴紧脸颊才有"胡须"的意思。
- 同一原则适用于尾巴、眉毛、腮红、衣领：任何**与主体断开**的细节，
  都会被读成噪点而不是造型。
- 判断方法不是看代码，是看放大后的 `preview.png`——
  如果某个元素第一眼不能被认出是"它应该是什么"，就说明该删或该收。

## 部件的语义由**遮挡关系**决定，不只由形状决定

同一个色块，画在主体**之上**是穿戴物，画在主体**之下**是长在身上的东西。
这一条比任何造型技巧都管用：用户看着一条 2px 的弧形尾巴说"这是披风还是尾巴"，
真正缺的不是加粗，是它被画在了身体下面——没有任何遮挡关系提示"这是披着的"。

想让一个部件读成 A 而不是 B，下面三条要同时成立：

1. **遮挡层级**：穿戴物（围巾/披风/背带/项圈）压在身体与四肢之上；
   肢体（尾巴/触须/触角）必须画在身体之前，被身体压住根部。
2. **横跨结构**：一条完整横跨颈/腰的带子是"非肢体"的硬信号。
   肢体不会横跨，只会从一侧伸出去。这一条最容易做到、也最有效。
3. **独立摆动**：穿戴物有独立于主体的活动量（垂片长度/角度随相位变化），
   肢体则是主体的一部分，跟着主体动。

反过来，只做"加粗 + 加深"而不动结构，是无效返工：
2px 的尾巴加粗成 4px 依然是尾巴，只是一条粗尾巴。

## 部件顶边不能比它上方的支撑体更宽

描边判据是"四邻存在透明像素就涂描边色"。部件的**顶行若比正上方那块实心体更宽**，
多出来的部分上邻是透明 → 整排被判成描边色 → 与上方自身的暗部连成一条黑杠，
读起来像"戴了个项圈"而不是"围在脖子上"，或者说像嘴巴漏出了黑边。

修法是让顶行宽度**收进**上方实心体的水平范围（本例：围巾顶行 9px
正好落在下巴实心区间 x=14..18 之内）。下半部分不受限，可以正常加宽。

同源的一个坑：**描边色的像素画在彩色部件上会打断该部件**。
本例中"嘴"的第三个收尾像素正好落在围巾上沿，把 4px 连续红色戳出一个洞。
凡是跨部件的极小结构（五官收尾点、发梢、褶皱高光），先确认它落在哪个部件的像素上。

## 逐像素字符网格 > 放大图

判断像素级问题时，除了 12× 放大图，再输出一份**字符网格**：
每个颜色反查一个字符，逐行打印，配合坐标标尺。

放大图能看出"有一条黑杠"，但看不出它由哪几个像素构成；
字符网格能直接定位到 `(16,20)` 这个具体像素，也能量出某一行真实可见宽度
（本例围巾顶行画了 9px、实际只剩 5px 可见 —— 这个数字靠肉眼看图是看不出来的）。

## 姿态：在同一角色上替换局部几何，不要画第二只角色

角色有多种姿态（坐 / 悬空 / …）时，抽一张姿态表覆盖**局部**参数，
不要复制整个绘制函数。两份绘制函数一定会各自漂移，改了一处忘了另一处。

姿态必须守住三条，否则它会读成"另一只角色"：

1. **辨识部件保持不变**：头顶毛、头、吻部、围巾围带。
   这些是品种识别点，动它们就换角色了。
2. **只改"受力会变的部位"**，且默认只改一处。
3. **姿态差异要克制** —— 见下节，这是本项目最贵的一条教训。

### 姿态差异要克制：宁可不动，也不要改坏

曾经给"悬空拖拽"定过一条规则——**差异必须同时出现在三个部位上才读得出来**。
照着做的结果是三个部位全是败笔：

- 眼睛从 2.0×2.2 撑到 2.3×2.6 → 32px 网格分辨率不出这个尺寸的圆，
  顶边被描边啃成锯齿，出来是两坨不规则怪块
- 腿改成两段椭圆串的斜棍 → 成了一根细棍加一个圆点，像骨头不像腿
- 身体 rx 收窄让腿根断开 → 头身比直接崩掉

**真正的教训**：小尺寸角色上"姿态不同"主要由**运动**表达，不由**造型**表达。
±2px 的钟摆摆动已经足够读出"被拎着"，造型一旦改动就是拿已有的辨识度换收益，
而 32px 网格几乎不允许任何造型改动还能保住辨识度。

实操准则：

1. 姿态表**默认只允许改一到两个部件**，其余全部沿用默认几何。
2. 优先挑"受力会变、且在 32px 上渲染得出来"的部位（本项目是垂耳）。
3. **不要为了表达情绪放大眼睛**。情绪靠眼态分支（睁/闭/眯）切换，不靠调尺寸。
4. 每次改姿态都把默认帧与姿态帧**并排 8 倍以上**看一眼。
   单独看姿态帧会自我感觉良好，只有并排才看得出"它变丑了"。
5. 删掉随之变死的分支，别留。残留的补丁路径是下一次改崩的直接原因。

### 整体位移放在绘制最后

摆动这类"整只角色平移"的效果，应当在所有图元画完后统一平移画布，
而不是给每个绘制调用都加一个偏移量。后者会让所有坐标都带上 sway，
改一处漏一处极难发现，而且逐个加偏移后描边判定也变了。

## 循环摆动的帧数由接缝决定，不是随便取偶数

钟摆式左右晃的偏移序列必须**首尾差 ≤1px**，否则循环点看得见跳动：

- 8 帧 `[+2,+1,0,-1,-2,-1,0,+1]` → 末帧 `+1` 到首帧 `+2` 差 1px ✓
- 6 帧 `[+2,+1,0,-1,-2,-1]` → 末帧 `-1` 到首帧 `+2` 差 3px ✗（明显卡顿）

所以"钟摆"这类动画要 8 帧而不是更省帧的 6 帧。
搭乘的次级动画（如布料）要走相邻相位，且分段处也要是相邻相位。

## 32px 里没有位置放"张嘴"

本例吻部底在 `y=19`、围巾围带顶在 `y=20`，**中间没有空行**。
任何"张嘴"变体（哪怕只有 2 行高的椭圆）都会落在围巾上，
把围带中间戳穿并与鼻头连成一整块黑，视觉上不是"惊讶"而是"一团黑"。

这是部件排布的硬约束，不是画法问题。解法有两个：

- 情绪改用**不占纵向空间**的部件表达（睁大的眼睛、上挑的眉毛、浮层符号）。
- 或者把围巾下移给嘴腾行，但要重新验证围巾顶行与下巴的描边关系。

**排布新部件前先量一遍相邻部件的边界**，确认有没有空行；
32px 网格上"看着有空间"和"真的有空间"经常不一致。

## 无边框方案下的点击热区

要"只显示角色、不显示底衬"时，按钮容器**仍需保留完整尺寸**作为
点击与拖动命中区，只是让它视觉上不可见。直接去掉容器会让热区随角色
轮廓的凹凸变化，边缘点击落空。

## 运行时切换动画

用 JS 驱动 `background-positionX`（Web Animations API 或 setTimeout），
而不是写一堆 `@keyframes`：

- 图集横向排列、多动画共享一张图时，CSS 方案会随帧数膨胀成规则泥潭
- **帧索引表和 `background-size` 的总帧数必须同源**。
  `background-size` 写死总帧数是最容易漏的一处：加一个动画后位移量对不上，
  表现是角色横向平移而不是换帧，而且完全不影响类型检查、构建也照样通过。
  正确做法是运行时从帧索引表求和，让它随动画增减自动生效。
- 状态切换只需换起始帧，天然支持
- 时长由 `帧数 / fps` 推导，改帧只需改元数据表

**不要用 GIF**：帧率受 GIF 自身控制，会与页面动画抢主线程；
且 GIF 无法按状态切换，只能整体替换文件。

## 目录与集成清单

```
scripts/pixel-pet/src/       生成器（无第三方依赖，PNG 用 zlib 手写编码）
src/renderer/public/<name>/  产物：spritesheet.png + pet.json + preview.png
src/renderer/components/     React 渲染组件
```

`preview.png` 是放大 4 倍、带棋盘格背景的校验图。**每轮改动后必须看一眼**——
像素画的错误（糊边、五官丢失、比例失衡）在代码里看不出来，在图里一眼就发现。

## 尺寸一致性陷阱

`BALL_SIZE` 这类常量常同时驱动视觉尺寸和拖动边界计算。
改视觉尺寸时必须同步定位常量，否则宠物会被裁切或拖出视口。
在代码里写明两者的耦合关系，否则后人只改一边就出 bug。

## 浅色 / 白色毛色的额外难点

白色角色不是"把调色板调浅"就完事，它有一整套独立的坑：

- **主白必须比 `#FFFFFF` 略暗**。纯白在白色或浅灰背景上会整个消失，
  边界完全读不出来。用暖白（`#F7F4EF`）这类略暗且带色相的白。
- **体积全靠内部阴影，不靠描边**。白毛加描边只会得到一个白色色块。
  必须主动画阴影：身体下缘、耳内侧、发缝、脸颊。
- **描边用暖深灰而非纯黑**。纯黑配白毛生硬，`#4A443E` 更接近真实长毛的阴影色。
- **预览底色要中性灰**。预览图的棋盘格若用浅灰白，白毛角色会失去轮廓，
  导致"描边够不够"无法判断。用 `#9A9AA0` / `#7E7E86` 交替。

### 细结构不能无差别描边

长毛的发梢、耳缘只有 2-3px 宽。如果对所有边缘像素无差别描边，
双侧描边会把这些部位**整个填满**，角色看起来像戴了顶黑帽子。

判据：判定边缘像素后，再检查其对侧像素是否也判为边缘。
若水平、垂直两个方向的两侧**同时**是边缘，说明这是 1-2px 宽的细结构，
此时跳过描边，保留填充色。封闭的头部/身体仍正常勾边。

### 五官会被阴影吃掉

白毛角色的五官全是深色，任何阴影画在五官附近都会直接盖掉它们。
阴影的半径与位置必须**先算好五官在哪，再避开**。
马尔济斯的眼睛在 y≈13，脸颊阴影就必须压到 y≥16 且缩小半径，
否则白犬的眼睛会整个消失——而且因为"脸还是白的"，看起来只是"没精神"，
很容易被误判成造型问题而不是遮挡问题。

## 预览图必须包含真实尺寸对照（最重要的一条）

**只在放大图上校验清晰度，是像素画最典型的自欺。**

4 倍预览里，1px 的眼白、浅阴影、双高光全都精致可辨；
但宠物实际只渲染 64px，这些细节会被邻接像素直接吞掉。
结果就是「预览图很好看，真机糊成一团」，而且很难从放大图上看出问题。

因此预览图必须输出两排：

| 排 | 缩放 | 用途 |
|---|---|---|
| 上排 | **1:1（实际渲染尺寸）** | 判定真机是否清晰 —— **以此为准** |
| 下排 | 4 倍 | 仅用于检查像素排布细节 |

在 32px 网格上做 UI 级美术，要主动**做减法**：
能省的层就省，用**实心深色 + 大高光**取胜，而不是靠层数堆精致。

### 同色部件必须有明度差

白爪画在白腿上、白色阴影画在白毛上，是"部件消失"的直接原因。
判断标准：把该部件和它的宿主并排放，明度差至少要跨一档。

浅阴影（`s` #D8D2C8）在白毛（`w` #F7F4EF）上明度差**不够**，
经 outline 描边后还会进一步吃掉。分隔必须用深阴影（`d` #B4AC9E）起步。

让小部件立住的三样东西：

1. **深色缝隙** —— 部件与宿主之间要有一圈，比宿主大 1px 的深色底
2. **分界线** —— 趾缝、毛缕，给出内部结构
3. **唯一彩色** —— 全身只留一处有彩色（肉垫、腮红），它是最容易被眼睛捕捉的锚点

## 图元函数的整数契约（死循环陷阱）

**所有图元函数只接受整数坐标**，传入浮点会出事。

最典型的翻车点是 Bresenham 直线：它的终止条件是 `x === x2 && y === y2`。
浮点坐标下步进会**跳过**终点——21.5 → 22.5 → 23.5，永远到不了 23——
循环永不退出，整个生成脚本挂死，且**不报错**。

这类 bug 的特征是：改完代码跑生成器，进程无输出地一直不结束。
此时应直接怀疑图元函数收到浮点参数，而不是去查渲染逻辑。

防御做法（图元内部自己兜住，不要指望调用方小心）：

- 入口处对所有坐标 `Math.round`
- 循环内加步数上限（画布对角线的 2 倍足够走完任何合法线段）

## 五官要实心，不要靠层数堆精致

**做减法，而不是加层。**

在 64px 这个实际尺寸上，"眼白 + 瞳孔 + 上眼睑线 + 双高光"四层画法
在放大预览里精致可辨，真机上眼白那 1px 环会被邻接像素吞掉，
眼睛退化成一团糊。

UI 级尺寸下正确的画法是**两层**：实心深色 + 单点高光。

- 深色块要用**比描边色更黑**的颜色，否则会和轮廓线混成一片
- 高光**单点、偏上左、左右对称**。双高光是放大图才成立的精致，小尺寸下反而杂乱
- 可以补一点下缘反光，防止眼睛变成纯黑洞
- 眼睛位置放在脸部**上半部**。偏下会显得"低头看人"

眨眼线用**实心深色**而非描边色，和睁眼同色系，状态切换才自然；
用描边色会和脸侧轮廓混在一起。

**判断眼睛是否被糊掉**，光看缩略图不够——把该区域的像素按字符打印出来：

```js
const toKey = (c) => !c ? '.' : c.map(v => v.toString(16).padStart(2,'0')).join('');
for (let y = 9; y <= 18; y++) {
  let row = '';
  for (let x = 8; x <= 24; x++) row += toKey(cv.data[y * cv.w + x]);
  console.log(String(y).padStart(3) + ' ' + row);
}
```

连续 4 个以上的同色字符，就是糊了。

## 品种辨识度：顶毛不能和脸同宽

画长毛犬时，头顶毛的宽度必须**明显小于脸宽**。
一旦顶毛与脸同宽，角色会读成狮子/玩偶而不是犬，
因为"鬃毛环抱面部"是狮子的视觉特征。
马尔济斯的正确结构是：窄顶毛 + 明显前突的吻部 + 垂耳 + 黑圆眼。

## 长毛犬的颈部围脖不能省

头和身体之间必须有**一圈蓬松的颈毛**。少了它，头会像"浮在身上的头"，
整体读不出是一个完整的生物。

关键在于三段式的宽度关系：**头 → 收窄的颈 → 宽肩**。

- 颈围**略窄于肩、宽于下颌**，两头都要卡住
- 若颈围和肩一样宽，三段结构塌陷，颈部就看不出"粗"了 ——
  长毛犬的颈部体积来自这个"比头宽、比肩窄"的收窄
- 围脖下缘要画阴影，与身体阴影连成一体，表现毛层叠压
- 加若干条分缕线，否则整块白看不出是长毛

注意五官与围脖的**高度冲突**：鼻头若下沉到围脖上沿之内，
会在吻部下方凭空冒出一个孤立黑点。鼻头 y 必须小于围脖上沿。
